# 驗收條件清單：交付前的最後一關

這裡放兩種文體的驗收條件。**寫完文章、交出去之前，用這份清單再檢查一次。**

- [`驗收條件_領域資源短文.md`](驗收條件_領域資源短文.md)
- [`驗收條件_方法論長文.md`](驗收條件_方法論長文.md)

---

## 為什麼需要這一關（不能靠自評）

`SKILL.md` 已經內建了強制查核關卡，寫作的 AI 會在交付時逐項回報通過與否。
**問題是那份自評不可信。**

真實案例（2026-08-06，第一篇正式交付文章）：交付時的強制關卡自評寫著
「專有名詞首次出現有括號說明 ✅」，實際上 API、XML、Cloudflare、READr、WTO、g0v
**六個都沒有說明**；自評「具體事實均有來源 ✅」，實際上查核總表漏了六類事實。

這不是能力問題。**同一條對話脈絡裡的 AI，會傾向確認自己剛做過的判斷**——
它記得自己「有在注意專有名詞」，於是打了勾，而沒有回頭逐個數。

解法只有一個：**換一雙沒看過產出過程的眼睛。**

---

## 三種用法（照你手上的工具挑一種）

| 你的工具 | 怎麼用 | 效果 |
|---|---|---|
| **Claude Code 等可派子代理的環境** | 派一個驗收代理，**只給它這份清單＋文章檔案路徑**，不給寫作過程、不給討論脈絡 | 最強：獨立脈絡、能實際開連結查證、能下載檔案抽驗 |
| **ChatGPT／Claude 網頁版等對話工具** | **開一個全新對話**，貼上這份清單＋貼上文章全文，不要貼討論過程 | 中等：一樣有「乾淨眼睛」的效果，查證能力視工具而定 |
| **不用 AI** | 當人工 checklist 逐條打勾 | 堪用：至少不會漏掉檢查項目 |

**關鍵不在有沒有代理，在有沒有「乾淨的眼睛」。** 開新對話就能拿到大部分效果，
任何人都做得到。

⚠️ 三種用法都有同一條鐵律：**不要把產出過程講給驗收者聽。**
一旦它知道你為什麼那樣寫，它就會開始替你辯護，而不是挑錯。

---

## 派工時要講的三件事

不管用哪種方式，開頭都要交代：

1. **產物在哪**：檔案路徑或全文
2. **這是定稿還是草稿**：定稿的話，任何留空記號、待補標記都算缺陷
3. **驗證環境**：如果文章引用的網站可能有地區限制（例如台灣政府網站常阻擋境外 IP），
   要請驗收者說明它從哪裡連線。**連不上不等於連結失效**，這種情況應回報
   「無法從此處驗證，需人工確認」，不可判定為死連結

## 收到結果之後

驗收結果分成兩種，處理方式不同：

- **這一篇的個別錯誤** → 修完就結束
- **skill 沒防住的「類型」** → 這才有長期價值。把它寫成規則提案放
  [`../../docs/`](../../docs/)，跟既有的證據文件並列

第二種是這套 skill 進化的主要來源。`SKILL.md` 現在那些查核規則，
每一條都是從一次具體犯錯長出來的。
