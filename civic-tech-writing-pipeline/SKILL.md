# 公民科技知識庫寫作技能（人機協同 pipeline）

## 概述與適用範圍

此技能協助「人＋AI」協作產製公民科技知識庫的文章。分工原則：

- **人負責**：問題設定、選題判斷、事實查核的最終把關、風格品味、讀者判斷
- **AI 負責**：素材整理、大綱結構、初稿撰寫、格式查核、主動標註不確定的資訊

成品定位是**工具型內容**：重點是好讀、可快速索引、方便 AI 抓取，不追求優美修辭。

**語氣護欄（重要）**：本技能一律採「就事論事」的介紹語氣——**少形容詞、少比喻、不堆疊華麗修辭**，把資訊清楚交代即可。這不是風格偏好問題，而是成品目的使然：資源介紹文的價值在於好掃讀、利於人與 AI 快速檢索，過多的形容詞與比喻反而會稀釋資訊密度、害了索引性。不同貢獻者使用本技能時，請維持這個一致、平實的語氣，不要讓 AI 自行發揮成雜誌式或論說式文風。

此技能不替使用者做最終事實把關。AI 必須主動標註每個事實的依據等級與待人類動作，但每個事實的最終確認責任在人。

## 文章類型（開始前先選類型）

選定類型後，篇幅、結構、語氣即自動依模板設定，不需逐項重新確認。

### 類型 A：方法論長文

| 項目 | 預設 |
| --- | --- |
| 目的 | 讓提案者知道「具體該怎麼做」，提供可直接執行的方法 |
| 讀者 | 公民科技提案者與貢獻者（技術與非技術背景皆有） |
| 篇幅 | 2,500 字以上 |
| 結構 | 依模板：結構化資訊區塊 → 這篇能回答你 → 問題場景 → 方法步驟 → 實際案例 → 常見陷阱 → 延伸資源 |
| 模板 | `templates/methodology-article.md` |

### 類型 B：領域資源指南

> **2026-08-13 更名並重新定義**（原名「領域資源短文」）：舊定義的讀者欄（提案者）與
> 篇幅欄（快速索引、不鋪陳）互相矛盾，第四篇把矛盾逼出來後改採現在的定義。
> 完整沿革見 `docs/SKILL規則的理由與沿革.md` §類型 B 更名。

| 項目 | 預設 |
| --- | --- |
| 目的 | 讓提案者看懂某領域既有專案「怎麼做的」，能借鑑其機制設計；同時兼顧「這個領域有哪些資源可用」的索引功能 |
| 讀者 | **正在規劃自己的專案、想參考既有做法的提案者**；以 AI 搜尋資料的使用者。⚠️ 不是「想使用這些工具的一般民眾」，兩者要找的東西完全不同，見 §2-0 |
| 篇幅 | 不設固定字數，**但不以精簡為目標**。完成標準是「提案者看完，知道這個專案解決什麼問題、怎麼運作、自己可以抄哪一段」。寫不清楚機制就是沒寫完，不要為了短而砍掉脈絡 |
| 結構 | 依模板：`#` 大標題 → 結構化資訊區塊 → 這篇能回答你 → 領域簡介 → 資源清單（小標題＋「提供者」「用途」「機制與可借鑑之處」三欄，非工具類連結列「延伸閱讀」） → 使用提醒 |
| 模板 | `templates/resource-list.md` |

### 兩種類型都不符合時

退回「完整必問清單」（見下節），逐題確認後組出客製規格。

### 新增文章類型的方式

在 `templates/` 新增一份模板（含 `#` 大標題與結構化資訊區塊範例、結構說明），並在本節補上類型定義表格。每個類型至少要有一篇實際文章放在 `examples/` 作為範例。

## 開始前必問

**已選定類型時**，只需確認三件事：

1. 這篇的主題與素材範圍是什麼？（明確說出「本篇素材限定為哪幾項」）
2. 手上已有哪些素材？（連結、文件、訪談筆記）
3. 有沒有必須包含或必須避開的內容？

風格對齊：請使用者提供個人風格檔（見 `styles/`）或一篇滿意的範文。若都沒有，採用本技能預設的中性語氣。

**未選定類型時**，完整必問清單：

1. 目標讀者是誰？
2. 有沒有可參考的範文？
3. 發布平台是哪裡？（影響字數、標題風格、連結格式）
4. 有沒有需要完全避開或必須包含的內容？
5. 這篇文章要讀者做到什麼？（了解、思考、行動）

## 共通寫作流程（階段門檻）

每個階段完成後，等使用者確認再進入下一階段。

**收合門檻**：使用者明確要求快轉時（例如「直接寫草稿看看」），可以把多個階段併在一輪完成。但收合的只是「停下來等確認」的節奏，**強制產物不可省**：讀後憑證、查核總表、查核關卡逐項結果仍須完整交付，不得因快轉而略過。

**模型切換提醒（2026-08-09 新增）**：軟性提醒容易被跳過（真實案例：同一次對話裡使用者
得自己主動問兩次「該用哪個模型」）。所以每個階段完成、等待使用者確認或已交付產出時，
**訊息結尾固定加一行**「下一站：<階段名>　建議模型：<Opus/Fable 或 Sonnet>」——
把提醒綁進一定會產出的東西，不是靠記性。使用者不切也照常繼續，不重複嘮叨；
AI 無法代切模型，只負責提醒。對照表：

| 階段 | 屬於哪一站 | 建議模型 |
|---|---|---|
| 1. 素材盤點、2. 大綱（含 2-1 關鍵詞實測的判讀取捨） | 站①：定範圍與驗收條件 | Opus／Fable |
| 3. 初稿 | 站②：實作 | Sonnet |
| 4. 事實查核（產出查核總表、走機械查核關卡） | 站③：驗證 | Sonnet |
| 4-2／6-1 獨立驗收發現的取捨（哪些採納、要不要推翻既有規則） | 站④：審查結果取捨 | Opus／Fable |
| 5. 風格套用、6. 交付（含發布、PR） | 站⑤：收尾 | Sonnet |

### 1. 素材盤點

這一階段的原則：**只用真正讀過的素材，而且要能證明讀過。** AI 不得用標題或印象拼湊摘要，必須交出只有實際讀過原文才生得出來的「讀後憑證」。這道關卡是後面事實查核的地基——地基沒讀實，後面再多查核也是建在沙上。

#### 1-1. 逐篇處理，交出讀後憑證（強制）

**一次處理一篇素材，不要整批囫圇吞。** 每篇都要產出以下憑證，缺一不可：

```
【素材 N 讀後憑證】
- 來源：[標題 / 機構]
- 連結：[URL]
- 原文引述：「[直接複製原文中一句關鍵句，不可改寫]」（來自：[逐字引用實際打開的網址，
  不是素材的主要連結]）
- 這句出現在：[第幾段／哪個小標下／文章前中後段]
- 重點摘要：[2-3 句話]
- 一個我原本沒預期的細節：[讀完才發現、光看標題猜不到的具體資訊]
- 用途：[預計用於文章哪個部分]
```

為什麼要這幾欄：

- **原文引述＋出現位置**——沒讀過就引述不出來，且引述若是杜撰，使用者一搜原文即可抓出。這是逼 AI 真讀的核心。
- **一個沒預期的細節**——瞎掰的內容通常籠統安全；真讀過才會冒出具體的意外。這一欄最難偽造。
- **引述的「來自」網址**——查一項資源常常會打開好幾個網址（首頁、說明頁、條款頁、
  母公司或關聯站），**每一句引述都要標出它實際來自哪一個網址，不能只寫在憑證開頭的
  「連結」欄裡籠統代表全部**。

##### 1-1-1. 引述來自不同網域時，要交代為什麼那是同一個主體（強制，2026-08-10 新增）

**查資料常常會從 A 網站點到 B 網站，這件事本身沒問題；問題是沒寫下「為什麼認為
B 網站講的就是 A 這個資源的事」。** 引述若來自跟這篇素材主要網址不同的網域，
讀後憑證必須額外寫一行**具體的連結依據**（例如：官方頁尾直接連過去、條款頁明講
「本服務由 X 提供」、DNS 子網域關係），不能只因為兩個域名字面相似或語意相關
就假定是同一個主體。**「看起來像」不是依據，要寫出實際點開、實際看到的連結路徑。**

真實案例（網域字面相似但實際不同主體，導致引述張冠李戴）見
`docs/SKILL規則的理由與沿革.md` §1-1-1。

##### 類型 B：讀後憑證必須含說明頁引述（強制，2026-08-09 新增）

**類型 B（領域資源指南）評估的每一項資源，讀後憑證必須包含該站說明頁**（`/about`、
「關於本站」、使用條款、資料來源說明等）**的引述**，只讀首頁與功能頁不夠。**沒有
說明頁要明講「這站沒有說明頁」**，不能默默跳過。

實例：某篇文章最嚴重的兩個錯誤（某資源的資料範圍限制、未收錄的功能項目）證據全在
`/about`，但當時的素材盤點只讀了首頁與功能頁。首頁講的是「這個工具能做什麼」，
說明頁才講「這個工具目前做到哪裡、不做什麼」——後者正是事實查核最容易出錯的地方。

#### 1-2. 讀不到的素材要主動講

若某篇素材因付費牆、連結失效、檔案過長等原因**沒有實際讀到，必須主動聲明「這篇我沒讀到，原因是 X」**，絕不默默跳過或用印象假裝讀過。沒讀到的素材不得列為文章依據。

**連線失敗不等於資源不存在。** 台灣政府網站可能阻擋境外 IP，而 AI 的網路出口通常不在台灣——AI 連不上，甚至使用者人在國外親測連不上，都不能當成「服務已下線」的證據，不可因此刪除條目。正確處理：條目保留、標「待查」（依據等級 ★☆☆☆☆），交由人類從台灣網路驗證後補完。同理，JavaScript 渲染的網頁用工具只抓得到空殼，「抓不到文字」也不等於「頁面沒內容」，應改用瀏覽器讀取或聲明讀不到。（實例：工程會「全民督工」頁面，境外一律連線被拒，台灣網路一開即通。）

##### 官網讀不到時，先找第三方權威資料庫或該資源自己的社群平台（2026-08-13 新增）

**讀不到官網不等於只剩二手摘要可用。** 宣告「讀不到」之前，先花一分鐘檢查兩個地方：

1. **同領域的權威第三方資料庫**：例如生物多樣性資料上 GBIF、政府資料集上
   `data.gov.tw`。這類平台的頁面通常是靜態、可讀的，且資料由該資源自己提交
2. **該資源自己經營的公開社群平台**：Facebook 公開社團、Instagram 等。很多專案的
   實際運作重心根本就在那裡，官網反而只是門面

找到的話，**依據等級可比照一手直讀，但必須在讀後憑證註明「這是替代來源，非原站自述」**，
不可寫成官網說了什麼。

真實案例（TurtleSpot Taiwan 官網讀不到、改用 GBIF 與官方社群找到更好來源）見
`docs/SKILL規則的理由與沿革.md` §1-2。

#### 1-3. 限定素材範圍

盤點後明確聲明「本篇素材限定為哪幾項」，不直接相關的素材列入「另文處理」，避免方向發散。

#### 1-4. 素材不足時的正確行為（強制）

**素材撐不起篇幅時，唯一不可接受的做法是用訓練知識填充。** 字數要求會製造填充壓力，
而填充出來的內容依據等級只有 ★★☆☆☆，依規則本來就不得寫進正文。

素材不足時，AI 必須停下來，提出下列其中一種提案交人拍板，不得自行硬寫：

1. **範圍收窄**：只寫素材撐得住的那一段，並說明收窄成什麼、為什麼
2. **補素材**：說明還缺哪一類佐證，由人提供或授權 AI 自行搜尋

**AI 自行補入的素材必須在盤點中標明「AI 自行補入」**，與使用者指定的素材分開列出，
並列入拍板清單。類型 B 的素材通常是指定清單，類型 A 則多半需要自行找佐證，
這條對類型 A 特別重要。

真實案例（指定題目頁大半空白，正確處理是提收窄而非填充）見
`docs/SKILL規則的理由與沿革.md` §1-4。

#### 1-5. AI 主動搜尋候選素材時，怎麼呈現給人拍板（2026-08-10 新增）

上一節處理的是「素材不足時才補搜」。**另一種情境是使用者一開始就同時給了指定清單與
搜尋範圍**（例如「甲方素材見這個連結，另外請你自己找，但不超過 3 個專案」）。
這種混合來源的用法適用以下流程：

**先列候選給人挑，不要逕自納入正文。** 找到候選後：

1. **每個候選附一句話「為什麼夠格」**，判準四項：現在就能用、非過時、跟主題直接相關、
   **查得到營運者且來源是該資源自己的官方頁面**（2026-08-10 新增第四項）。第四項查不到
   不等於自動剔除，但要在候選說明裡明講「營運者不明」，交由使用者決定要不要收，
   不能默默寫上一個提供者名稱交差
2. **候選數量比上限多列一兩個**，讓人有得挑；不要剛好湊滿上限，那等於沒得選
3. **一次把所有待拍板的事情問完**（哪些候選要收、指定素材裡有問題的要不要留、
   分類怎麼歸），不要邊讀邊問。**拍板後才進入 §1-1 的讀後憑證流程**
4. 拍板結果與理由寫進讀後憑證檔案，AI 補入的素材與指定素材**分兩節列**

為什麼要先拍板再深讀：讀後憑證是重工序（每篇要讀說明頁、找逐字引述、挖意外細節）。
先深讀再給人挑，被剔除的那幾篇工就白做了；更糟的是沉沒成本會讓 AI 傾向替已經
讀完的素材說話。

**指定素材與搜尋規格衝突時，停下來問，不要自己判。** 常見情形：使用者說「非台灣的
資源只收 open data 類」，但甲方指定清單裡就有非台灣、非 open data 的工具。那條規格
限制的是新素材還是全部，只有使用者能決定。

兩則真實案例（先拍板再深讀的理由；第四項判準「查得到營運者」的緣由）見
`docs/SKILL規則的理由與沿革.md` §1-5。

### 2. 大綱

提出含每節主旨的大綱與預計字數。**等使用者確認後才開始寫**。

#### 2-0. 讀者對位檢查（強制，大綱的第一段就要寫，2026-08-13 新增）

**大綱送出時，開頭必須先寫這三行，寫在章節結構之前：**

```
本篇讀者：（直接抄類型定義表格「讀者」欄的原文用詞，不得自行改寫或概括）
他們會怎麼找到這篇：（這個讀者實際會用的問法，不是我們希望他們用的問法）
讀完要能做什麼：（一句話，具體到可以驗證）
```

**三行任一與類型表格的讀者定義對不上，就不得進入 §3 初稿。**

##### 為什麼這道關卡要存在，而且要用「寫出來給人看」的形式

**它防的不是「AI 沒給人看大綱」，是「給人看了、雙方都沒發現方向錯了」。** 第四篇曾經
整篇寫給錯的讀者、一路通過所有關卡直到交付後才被發現，根源是大綱只呈現章節與字數，
沒有呈現「這是寫給誰的」。這一條的機制是把判斷材料攤到人面前、讓人有機會否決，
不是多一道 AI 自我檢查。完整事故經過見 `docs/SKILL規則的理由與沿革.md` §2-0。

#### 2-1. 關鍵詞實測（大綱定稿後、下筆前）

這一階段的原則：**領域名與章節用詞不能靠直覺，要實測能不能被檢索到。**
自創領域名在檢索上實測是零（不是詞沒選好，是整個類別都不該用）。詳細證據見
`docs/AI可讀性規範的依據.md` 三、B 組「領域名沿用既有常用詞」條目。

**步驟**：

1. 列候選詞，四類各三到五個：領域既有名稱（若專案本身已有交付清單或問卷選項用的名稱，
   優先沿用）、使用者的任務問法（動詞句，如「政府標案哪裡查」）、同義與上位詞、
   打算沿用或自創的圈內詞（這類是要被驗證的對象，不是預設可用）
2. 逐詞實搜，記錄：前 10 條結果是不是同一個領域、誰在佔位、我們要推薦的資源有沒有出現。
   **檢索面規則見下方 2-1-1，不是只搜一個地方就算數**
3. 判讀後回填。**下列四個位置各自獨立，不可只測其中一個就套用到其他位置**：
   - **主標題**（`#` 大標題）
   - **核心主題那一行**（結構化資訊區塊第一欄）
   - 各節標題
   - 主題標籤

   ⚠️ **主標題要單獨測過候選詞才能定稿，不是核心主題的附屬品。** 主標題與核心主題
   服務的目的不同：核心主題要完整交代「領域＋文體＋適合誰」，主標題要讓人願意點進來，
   兩者的用詞取捨不一樣，直接把核心主題的詞套進標題會出事。
   **主標題與核心主題若各自扛不同的詞，要檢查合起來有沒有漏掉必要的限定詞**
   （見下方實例）。

   > 實例（2026-08-10，類型 B 第三篇）：只測了核心主題的詞，主標題直接沿用同一批詞
   > 草擬成「意見要投到哪裡？」，被使用者退回——這批工具做的是「整理多方利害關係人的
   > 討論」，不是「投遞意見」，而且 Polis 的核心動作剛好也叫投票（對主張投同意／不同意），
   > 混用會誤導。回頭補測第二輪才發現「意見整理」這個詞前 10 條全是日文結果，同樣不能用。
   > 定稿的主標題「一群人的意見怎麼收斂成共識？公民參與管道與討論工具整理」不含
   > 「公共政策」這個限定詞，而實測顯示「意見」「共識」缺了公共政策限定會整批落到
   > 企業管理領域，因此該限定詞改由核心主題那句話扛——**這就是「兩個位置要合起來檢查」
   > 的意思**。

   ⚠️ **主題標籤的候選詞不可以是特定工具／產品／品牌名稱**，即使該工具在領域裡是
   最知名、最核心的代表。主題標籤是領域分類詞，不是資源清單裡任何一項資源的名字——
   資源名稱已經在資源清單裡出現，標籤重複放一次沒有分類作用，反而可能讓讀者誤以為
   該工具能代表整個領域。

   ⚠️ **回填結果要對候選詞表自己的判讀負責，不能自相矛盾。** 寫回填結果前，先回頭
   核對候選詞表每一列的「判讀」欄：被判「好戰場」「可用於主題標籤」的詞若確實符合
   需求就該用，被判「淘汰」的詞絕不能出現在任何回填欄位。這條聽起來是常識，
   但實戰中發生過同一份檔案裡候選詞表判某詞可用、回填結果卻寫了另一個從未測過的詞。

   > 實例（2026-08-10，類型 B 第三篇）：候選詞表明確判讀「數位民主」→「可用於
   > 主題標籤」，回填結果卻寫「主題標籤：⋯Polis」——「Polis」是資源清單裡一項工具的
   > 名字，從未被列為候選詞測過。這個矛盾在同一份檔案裡沒被自己發現，交付前的獨立
   > 驗收（見 §6-1）也只核對「文章的標籤是否忠實抄自回填結果」，沒有再往上一層核對
   > 回填結果本身是否忠實反映候選詞表的判讀——兩段話錯得一致，反而沒有觸發任何一道
   > 關卡（對應的驗收條件已同步修正，見 `checklists/` 兩份）。
4. **產出交付物（強制，2026-08-09 新增）**：把候選詞、逐詞觀察與判讀結論存成一份檔案，
   放在 `_驗收紀錄/<短文／長文>_<領域>_檢索詞實測.md`（命名比照查核總表、讀後憑證
   的既有慣例，跟這篇文章的其他內部檔案放同一個目錄）。**這份不是選配**——沒有它，
   驗收時無法確認核心主題、章節標題是不是真的依實測結果回填，還是憑直覺寫的；
   `短文_法律立法歷程與議會監督.md` 那篇跳過這一步，是漏洞被發現後才補這條規則的
   實例，見下方格式範本

**檔案格式範本**：

```markdown
# <短文／長文>_<領域>_檢索詞實測

實測日期：YYYY-MM-DD

實測檢索面：（例如「Google 網頁搜尋、Bing」。**必填，只測一個也要寫明並附理由**）

## 候選詞

| 詞 | 類別 | 前 10 條結果觀察 | 判讀 |
|---|---|---|---|
| （詞一） | 領域既有名稱／任務問法／同義上位詞／自創詞 | 是否同領域、誰在佔位、我們要推薦的資源有沒有出現 | 淘汰／改攻長尾問句／好戰場／內容農場佔位可搶 |

## 回填結果

- 主標題：（沿用原案／改成哪句話，附一句話說明依據）
- 核心主題（或核心方法）：（沿用原案／改成哪句話，附一句話說明依據）
- 章節標題：（有沒有調整，附一句話說明依據）
- 主題標籤：（最終選用哪幾個詞）
- 合併檢查：（主標題與核心主題合起來，有沒有漏掉必要的限定詞）
```

判讀對照表與三條防塞詞紅線見 `docs/AI可讀性規範的依據.md` 三、B 組「關鍵詞選用要實測」條目。

#### 2-1-1. 檢索面規則（2026-08-10 新增）

**「逐詞實搜」要指定在哪裡搜，否則預設只會有一個檢索面而沒人發現。**

- **Google 必測。** 台灣市占約 82.7%（StatCounter，2026-02），且是 Gemini 與
  Google AI Overviews 的來源
- **第二個檢索面預設 Bing。** 理由不是它排第二（台灣第二名是 Yahoo 奇摩，約 10.8%，
  Bing 約 5.9%），而是 **Yahoo 奇摩的自然搜尋結果由 Bing 提供**，測 Bing 等於一併涵蓋
  Yahoo 奇摩，合計約 16.6%；且 Microsoft Copilot 直接建在 Bing 索引上
- **若當次有理由改測別的檢索面，在交付物寫明理由**，不必硬綁 Bing

**沒有任何單一索引能涵蓋所有 AI 助理**，所以這裡的目標不是「測全」，是「不要只測一個
卻沒人知道」。目前各家的檢索來源分歧：Copilot 用 Bing、Gemini 用 Google、
Claude 用 Brave 的獨立索引、ChatGPT 已改用自家索引（OAI-SearchBot）、
Perplexity 用自家索引。

##### Google 被反自動化機制擋下時怎麼辦（2026-08-15 新增）

AI 的網路出口不是真人瀏覽器，實測時常被 Google 判定為異常流量、跳出驗證頁。
**遇到這種情況，不得嘗試繞過驗證機制。** 依下列步驟處理：

1. **改以 Bing 為主檢索面，另加一個 AI 助理的檢索面**（例如 `WebSearch` 工具，
   若其索引來源與 Bing 不同）當交叉對照，兩者合計仍能覆蓋多數判讀情境——
   多數淘汰或收錄的決定，依據的是語意漂移（詞被別的領域佔用）或自創詞離散
   （檢索結果整批不相關），這兩種訊號**在哪個搜尋引擎測都看得出來，不會因為
   換成 Google 而翻盤**
2. **在交付物開頭的「實測檢索面」欄位具名寫出 Google 缺測**：寫明理由（反自動化
   機制擋下）、缺口本身（Google 佔台灣市占約 82.7%，是 Gemini 與 AI Overviews
   的來源），不得只寫「本次測了 Bing」而略過缺口
3. **升級條件（何時才需要真人手動查證）**：某個候選詞的判讀會**直接改變主標題
   或核心主題**，且 Bing 的結果**不是明確的語意漂移**（也就是說，看起來只是
   「排不進前 10」而不是「意思根本不對」）——這時才請使用者用自己的瀏覽器
   （真人不會被擋）手動查那 2-3 個關鍵詞，不必為了覆蓋率把候選詞全部查一輪

這條規則刻意不要求「每次都真人手動查全部候選詞」：手動查是機械性的資料蒐集，
真正容易出錯的是**判讀**（例如把「被自己要推薦的資源佔位」誤判成「被競爭者佔位」，
見 GIS 篇「地圖協作」一詞的實例），多測一個索引不會修正判讀錯誤，只會把更多資料
餵進同一套可能出錯的判讀裡。把真人的查證力氣留給真正影響結論、且結果本身模稜兩可
的少數詞，比全面手動搜尋更划算。

⚠️ **交付物開頭的「實測檢索面」欄位是強制的。** 只測一個檢索面不是錯，
**不寫明只測了一個才是錯**——沒寫，驗收時無從得知這份實測的覆蓋範圍。

立規緣由（連續兩篇都只測 Google 且未交代）見 `docs/SKILL規則的理由與沿革.md` §2-1-1。

**執行方式**：候選詞少於 5 個，主線直接搜；**15 個以上，派 `researcher` 這類研究型子代理
批次執行**，只給它候選詞清單與判讀對照表（不給討論脈絡），主線只收判讀後的結論表——
這件事的形狀就是「大量網頁研究、只要附來源的結論」，扛住十幾份原始搜尋結果不該留在
主線對話裡。**不管走哪條路徑，步驟 4 的交付物都要產出**，候選詞少不是省略它的理由。

### 3. 初稿

依所選類型的模板撰寫。每個具體事實（數字、機構名稱、功能描述）標註對應來源。此階段以結構與正確為優先，不追求文字優美。

### 4. 事實查核

這一階段的分工原則：**AI 負責誠實標註不確定，人負責最終拍板。** AI 不替使用者決定真假，只負責把可疑的東西主動舉手講出來，讓使用者的查核從「逐句抓鬼」變成「審一張清單」。

#### 4-0. 查核分工（誰把關什麼）

- **AI 把關**（人類不必重做，抽查稽核即可）：連結有效性、一手來源逐字比對、跨來源混寫檢查、譯名檢查、時效性標記、範圍型陳述的資料層抽驗。
- **人類把關**（AI 做不到或不該做）：AI 連不上的來源、涉及人的事（掛名、聯絡當事人）、編輯判斷（收錄與否、語氣、定位）、抽查稽核 AI 的讀後憑證、最終拍板。

#### 4-1. 查核總表（強制，全文一張）

初稿寫完後，AI 必須產出一張涵蓋全文的「查核總表」，逐項列出每個事實陳述。不可省略、不可只挑幾項做、不可用一句「大致沒問題」帶過。**需要人類介入的項目排最上面**，其餘標「無—可抽查」。

⚠️ **這張表是內部工作檔，不進發表的文章**（見 §6）。它與文章並存為獨立檔案，交付時一併附上。
格式如下：

```
【查核總表】
| 事實陳述 | 位置 | 依據類型 | 依據等級 | 還缺什麼（待人類） |
| --- | --- | --- | --- | --- |
| [事實 1] | 第 N 節 | 讀不到來源 | ★☆☆☆☆ | 查證：[具體可執行的一句話] |
| [事實 2] | 第 N 節 | 推斷（依據為何） | ★★★☆☆ | 判斷：[要人決定什麼] |
| [事實 3] | 第 N 節 | 逐字引文 | ★★★★★ | 無—可抽查 |
```

「還缺什麼」必須是可執行的一句話，開頭標明動作類型：**查證／判斷／聯絡／拍板／無**。這欄是給人類的工作清單；依據等級是給 AI 的紀律機制，兩者用途不同、缺一不可。

依據等級定義（每一級綁定「依據類型」與「預設人類動作」）：

| 依據等級 | 依據類型 | 預設人類動作 |
| --- | --- | --- |
| ★★★★★ | 一手來源逐字可查，無時效風險 | 無；整批抽查一兩條稽核即可 |
| ★★★★☆ | 逐字可查或資料層抽驗，但含時效性事實或抽驗範圍有限 | 無需重驗；正文須帶時間限定詞 |
| ★★★☆☆ | 推斷（結構性證據、多來源拼湊）或來源可能過時 | 需人類介入，「還缺什麼」欄必須寫明是查證、判斷還是聯絡 |
| ★★☆☆☆ | AI 推測，原文沒明說 | **不得寫進正文**；查證後才能升級 |
| ★☆☆☆☆ | 查無來源或讀不到 | 正文標「待查」；需人類用 AI 摸不到的管道處理 |

**特別針對以下四類最容易出錯的情況，依據等級一律不得高於 ★★★☆☆，並主動說明：**

1. **金額、數字、年份**：容易張冠李戴掛錯對象（例：把某平台的金額誤掛到另一個專案）
2. **某風險／某結論的歸屬來源**：容易把「A 報告講的事」誤說成「B 機構自己承認的事」
3. **專有名詞的中文譯名**：查無官方譯名時保留英文，**絕不自創**，依據等級標 ★☆☆☆☆
4. **範圍型陳述**（涵蓋範圍、開放程度、清單完整性）：只讀到頁面說明最多 ★★★☆☆，必須抽驗實際資料內容（下載檔案、數筆數、比對子集）才能升到 ★★★★☆。「官方頁面存在」不等於「內容如推斷」

##### 取證方式也要分級：一手直讀 vs 工具二手摘要（2026-08-10 新增）

**「我讀過原文」與「工具告訴我原文寫了什麼」是兩件事，依據等級不同。**

| 取證方式 | 這是什麼 | 依據等級上限 |
| --- | --- | --- |
| **一手直讀** | 用瀏覽器工具載入頁面，**原始文字進入 AI 自己的上下文**，AI 親眼看到那些字 | ★★★★★ |
| **工具二手摘要** | `WebFetch`／`WebSearch` 抓取頁面後，**由另一個模型讀原文並產出摘要**回傳。AI 從頭到尾沒看過原文，看到的是另一個模型的轉述 | **★★★★☆**，且「還缺什麼」欄須寫「查證：建議人工開原文核對」 |

這不是「看得清楚 vs 看得模糊」的差別，是**看過 vs 沒看過**的差別。轉述的模型可能漏講、
改寫、把不同段落併成一句，而 AI 沒有原文可對照，無法察覺。**工具回傳的「逐字引述」
同樣不可信**——那個字串也是轉述模型產生的，可能是重建而非複製。

**這一格與 ★★★☆☆「AI 自行推斷」要分開，兩者是不同性質的不確定性**：二手摘要是
「證據存在但我沒親眼看」，推斷是「我看到了證據但結論是我自己跳的」。

⚠️ **具體數字、法規條文、逐字引文若只有二手摘要支持，交付前應補做一手直讀。**
兩個工具查證得到一致答案，也不能取代自己讀一次原文。

實證（三項數字補做一手直讀後，全都撈出摘要漏掉的實質內容）見
`docs/SKILL規則的理由與沿革.md` §4-1。

#### 4-1-1. 依據等級的區位解釋（給使用者設定自己的護欄）

五個等級不是均勻的刻度，真正的斷層在 **★★★★☆ 與 ★★★☆☆ 之間**——上面兩級 AI 在
「轉錄」，下面三級開始「推理」（從證據跳到結論，跳的那步是 AI 自己的）。**預設的人工
介入線畫在 ★★★☆☆（含）以下**，這條線已經寫進上方的依據等級表；★★☆☆☆ 那條「不得
寫進正文」的線不開放調鬆。想調整護欄鬆緊、或想理解每一級具體會怎麼出錯，
完整說明見 `docs/SKILL規則的理由與沿革.md` §4-1-1。

#### 4-2. 強制查核關卡

通過下方的強制查核關卡（見「事實查核關卡」一節），向使用者回報逐項結果，由使用者做最終確認。**使用者只需處理查核總表「還缺什麼」欄有指名動作的項目**，其餘整批抽查一兩條稽核即可，這是查核總表替使用者節省查核工的核心。

### 5. 風格套用

依使用者的風格檔或範文調整語氣。若初稿語氣與目標風格落差明顯，**從頭重寫比逐句修改更有效**。

### 6. 交付

一篇文章「完成」的定義是「文章本體＋內部查核總表＋skill 規則提案清單」三件齊備，
**只有第一項發表**：

| # | 產物 | 進不進發表的文章 |
|---|---|---|
| 1 | 文章本體（`#` 大標題、結構化資訊區塊、文末的資料查核說明與**授權與出處**，不含 frontmatter） | ✅ 是 |
| 2 | 完整查核總表（含依據類型與依據等級） | ❌ **否，另存內部檔** |
| 3 | skill 規則提案清單（見 §6-5，本篇沒有新發現也要明寫「無」） | ❌ **否，另存內部檔** |

文章本體裡「資料來源清單」這個獨立區塊**依文體決定要不要**：

- **類型 A（方法論長文）保留。** 長文的事實來源不會全都是內嵌連結，需要獨立列出。
- **類型 B（領域資源指南）不設這一區。** 資源清單表格與延伸閱讀本身就是連結，
  來源已經在正文裡，不必再抄一份佔篇幅。

**查核總表與 ★ 五級量表是產製流程的內部工具，不得出現在發表的文章裡。**
連同「待人類」「讀後憑證」「強制查核關卡」「（發布時狀態）」這些詞彙，一律留在內部檔案。
理由：讀者要的是「這篇查過沒有、我能不能自己複查」，不是產製過程的稽核軌跡；
把一整張含星等的表貼在文末，對讀者是雜訊，對發布平台是稀釋內容。

「資料查核說明」該寫什麼：**一句話**，查核日期＋提醒讀者內容可能已變動、請自行查核。例如：

> 本文資料查核日期：2026-08-07。資料庫、各類工具與社群討論筆記，均有可能在此日期之後更新、
> 變動，請務必自行查核。

不寫查核細節、不寫核對了哪些類型的事實——那些是給委託方看的，屬於內部查核總表的內容。

第 2 項的內部查核總表**仍然強制產出、不得省略**（見 §4-1），只是改為與文章並存的獨立檔案，
交付時一併附上。它是委託方抽查稽核的依據，也是下一次修訂的起點。

#### 6-0. 查核發現，哪些寫進正文、哪些留在內部檔

查核過程會發現兩種不同性質的東西，處理方式不一樣：

- **「讀者要用這個工具／資訊就必須知道的事」→ 寫進正文。** 例如：某個通報系統無法匿名、
  需要哪些必填欄位；某個工具依賴的上游服務不穩定。這些是使用門檻，漏講會讓讀者白跑一趟。
- **「我是怎麼查證這件事的」→ 留在內部查核總表，不寫進正文。** 例如：抽驗了幾筆資料、
  用什麼方法換算、查證當下連線環境如何。這些是產製過程的稽核軌跡，對讀者沒有使用價值，
  只會讓正文變得像除錯紀錄。

判準是**讀者用得到，還是只有委託方查核時用得到**。分不清楚時，預設留在內部檔——
正文只留讀者真正需要的那句話。

（這條規則的來源與早期範例文章的過時示範，見 `docs/SKILL規則的理由與沿革.md` §6-0。）

⚠️ **改動本節時，`checklists/` 兩份驗收條件裡對應的條目必須同步修改**，
否則獨立驗收員會照舊條文把「查核總表缺席」判成缺陷——那是假陽性，且會排在報告最前面。
（實例見 `docs/規則資產同步的診斷與提案_2026-08-07.md` 摩擦 3。）

#### 6-1. 交付前送獨立驗收（強制）

**寫作者的自評不可信。** 同一條對話脈絡裡的 AI 會傾向確認自己剛做過的判斷——
它記得自己「有在注意專有名詞」，於是在強制關卡打了勾，卻沒有回頭逐個數。

（實例：某篇交付文章自評「專有名詞首次出現有括號說明 ✅」，實際有六個縮寫沒有說明；
自評「具體事實均有來源 ✅」，實際查核總表漏了六類事實。）

所以交付前必須換一雙沒看過產出過程的眼睛，用 [`checklists/`](checklists/) 底下對應文體的
驗收條件重檢一次。有子代理環境的派代理、只有對話工具的**開一個全新對話**貼清單與全文、
兩者皆無的當人工清單逐條打勾——**關鍵不是工具，是驗收者沒看過你的產出過程**。
用法與注意事項見 [`checklists/README.md`](checklists/README.md)。

#### 6-2. 決定發布位置

文章放到哪個網址上，**影響大於本 skill 所有格式規則的總和**——寫得再合規，
放在爬蟲讀不到的網址等於沒發布。交付前先讀 [`發布指引.md`](發布指引.md)，
至少確認三件事：即時取用型 AI 爬蟲沒被 robots.txt 擋、頁面沒有 `noindex`、
**正文在原始 HTML 裡而不是靠 JavaScript 載入**。第三項最常被忽略，
因為用瀏覽器看一切正常。

#### 6-3. 授權（強制，且不得選更嚴格的）

**每篇文章都必須標示授權，這一項不可省略。** 授權**必須是 CC BY 4.0，或比它更寬鬆**
（例如 CC0）。**不得選擇更嚴格的授權**——不得加上 SA（相同方式分享）、NC（非商業性）、
ND（禁止改作）。

##### 為什麼禁止更嚴格

一句話：**加嚴擋不住 AI（訓練常常不需要授權），卻擋得住人**（NC 讓媒體不敢引用、
ND 斷了翻譯與改寫、SA 會傳染給再利用者的整個專案）。付出成本、得不到保護，所以不做。
完整論證（含 Creative Commons 官方說明原文）見 `docs/SKILL規則的理由與沿革.md` §6-3。

##### 授權種類速查

| 授權 | 可以嗎 | 說明 |
|---|---|---|
| CC0 | ✅ 可以 | 放棄所有權利，比 CC BY 更寬鬆。想完全不設限時用 |
| **CC BY 4.0** | ✅ **預設用這個** | 可自由使用、改作、商業利用，只要標示出處 |
| CC BY-SA | ❌ 不可 | 加了「衍生作品必須用相同授權」，會傳染給再利用者的整個專案 |
| CC BY-NC | ❌ 不可 | 禁止商業利用，媒體與多數機構會直接放棄引用 |
| CC BY-ND | ❌ 不可 | 禁止改作，翻譯、摘要、改寫都不行，等於斷了在地化的路 |

##### 標在哪裡

**正文結尾的「授權與出處」區塊，這是唯一必須存在、也唯一發布後真正存在的地方。**
本 skill 已不使用 frontmatter（見 §6-4），所以不存在「兩個地方都要標」的問題——
授權只有這一個位置，缺了就是沒標。

##### 想讓 AI 標示出處、把讀者導回來源，該怎麼做

沒有任何授權能強制 AI 講出處（CC 正在開發的 CC Signals 框架現階段還不能用，理由見
`docs/SKILL規則的理由與沿革.md` §6-3）。做得到的是把歸屬與正典網址**寫進正文的文字裡**——
爬蟲抓走的是內文，frontmatter 抓不到、頁尾圖示也常抓不到。一句寫清楚「這篇來自誰、
更多資源在哪個網址」的完整句子，才是 AI 引用時真的會帶走的東西，這跟本 skill
「事實寫成可獨立引用的單句」是同一個機制。

#### 6-4. 不使用 frontmatter，文章以 `#` 大標題開頭、緊接結構化資訊區塊（2026-08-12 更正）

**本 skill 已不使用 `---` 到 `---` 的 YAML frontmatter 區塊，任何新產製的文章都不加。**
文章開頭固定是：一行 `#` 大標題（唯一的標題來源），空一行後緊接「結構化資訊區塊」。

##### 為什麼拿掉（沿革）

一句話：frontmatter 對任何發布平台都沒有正面作用（HackMD 從 2023-06-20 起就不讀取），
卻兩度造成實際傷害（稿件經 Google Docs 編輯時被渲染成擠成一團的大標題）。
只有成本、沒有效益的東西，拿掉就好。完整查證過程與沿革見
`docs/SKILL規則的理由與沿革.md` §6-4。

##### 結構化資訊區塊本身的規則不變

`#` 大標題之後緊接的「結構化資訊區塊」，取代舊版的「本文重點」：一組固定順序的
「標籤：內容」短句，不加 `##` 標題。**類型 B（領域資源指南）六欄：核心主題（含適用
對象）、涵蓋資源、主題標籤、資料查核日期、作者、授權**——「適用對象」併進「核心主題」
那一句話裡（見下方「AI 可讀性規範」第 2 項），理由是實測 HackMD 的摘要截斷長度只有
約 100 字（`#` 大標題也算在內），核心主題那句話要同時扛起「領域＋文體＋適合誰」，
欄位越少越不會被擠出截斷範圍。**類型 A（方法論長文）七欄：核心方法、適用情境、
方法步驟、主題標籤、資料查核日期、作者、授權**。這個區塊同時滿足三件事：

1. **HackMD 上的搜尋摘要**（從內文開頭截取，含 `#` 大標題在內約 100 字）抓到的就是
   大標題＋這個區塊
2. **貼到 Medium／方格子時可以直接當開場段落**，不用另外重寫
3. **標籤化格式對人掃讀也友善**，不需要組織成完整段落才能理解重點

**發布到 HackMD 時，標題還是要在編輯器的標題欄位另外打一次**——正文裡的 `#` 大標題
是給 Google Docs／Medium 這類沒有獨立標題欄位的中繼工具用的可見標題，不能取代
HackMD 編輯器的標題欄位。

##### 6-4-1. 修訂舊稿件時的 frontmatter 清理

修訂 2026-08-12 前產製的舊稿件時，這是**唯一**還可能撞到 frontmatter 的情境。
操作規則見 [`修訂既有文章.md`](修訂既有文章.md) 第 2 節。

#### 6-5. skill 規則提案清單（強制，2026-08-09 新增）

**規則提案沒有交付物就會靜靜蒸發。** 實例：一次獨立驗收找出「資源網站的 `/about`
是必讀素材」這條高價值規則，寫進了查核總表，但兩天內沒有任何機制檢查它有沒有真的
搬進 `SKILL.md`——直到下次盤點才發現它從沒被搬過。§6-1 獨立驗收、修訂既有文章時
常常會冒出「這不是這篇的錯，是 skill 沒防住的類型」，這類發現若只留在
查核總表裡，跟沒發現一樣。

**格式**（與文章並存的獨立內部檔，交付時一併附上）：

```
【本篇產生的 skill 規則提案】
| 發現 | 建議規則 | 去處（哪個檔案／哪個 PR） | 狀態 |
| --- | --- | --- | --- |
| [這次撞到的具體現象] | [提案怎麼改] | [SKILL.md §X／templates／checklists] | 未搬運／已開 PR #N／已併入 |
```

本篇若沒有產生新發現，仍要明寫「本篇無新規則提案」，不能省略整節不寫——
省略跟「忘記檢查」在效果上是一樣的。

**牙齒**：這一節所有項目的狀態都不是「未搬運」，才算交付完成（見上方 §6 交付產物表
第 3 項）。狀態卡在「未搬運」超過一篇文章的週期，代表這條發現正在蒸發，下次交付前
要主動處理，不能無限期擱置。

### 7. 修訂既有文章（不是從零寫的情況）

依驗收發現、使用者批改意見修訂已交付的文章時，前面的階段門檻大多不適用——
不需要重跑素材盤點或大綱，但有從零寫時不會發生的操作規則要遵守，見
[`修訂既有文章.md`](修訂既有文章.md)。

## 語言與格式規範（台灣繁體中文）

- 全程使用台灣用詞，嚴格避免中國慣用詞彙，常見對照：
  - 軟件 → 軟體｜視頻 → 影片｜網絡 → 網路
  - 鏈接 → 連結｜點擊 → 點選｜信息 → 資訊
  - 獲取 → 取得｜平臺 → 平台｜賦能 → 培力
- 不確定某詞是否為台灣用法時，以台灣媒體日常用語或教育部國語辭典為準
- **「臺灣」一律用「臺」，不用「台灣」**（2026-08-10 新增）。這是指國名本身；
  其他詞彙裡的「台」不受影響（例如「平台」維持上方對照表的用法），
  機構或資源的**自稱正式名稱**若本身用「台」，依前述「資源名稱以自稱為準」規則，
  不強制改成「臺」（見事實查核關卡「資源名稱」條）
- **標點符號一律使用全形**（，。、？！：；「」）。數字、英文單字、程式碼與網址維持半形
- **避免使用破折號（——）**：改用句號拆成兩句、用冒號帶出說明，或用括號補充
- 每個段落只傳達一個核心概念；重要資訊放前面，細節放後面
- 語氣中性易讀，像在跟讀者說話，不像交報告；不堆疊形容詞

## AI 可讀性規範

讓文章同時對人類讀者與 AI 檢索友善：

1. **不使用 frontmatter**；文章開頭是 `#` 大標題，緊接結構化資訊區塊取代舊版「本文重點」。
   完整規則見 §6-4，發布時的操作規則見 `發布指引.md`
2. **結構化資訊區塊的字數要精打細算**：**實測 HackMD 只截前約 100 字**當自動摘要，
   `#` 大標題也算在內，只給機器看的欄位（主題標籤、日期）要排在核心主題／核心方法之後，
   不能擠占開頭那段稀缺字數
3. **領域名與章節用詞沿用既有常用詞，不在寫作時自創**：自創的領域名在檢索上實測是零
   （不是換個詞的問題，是整個類別都不該用在核心主題與標題裡）。大綱定稿後、下筆前
   做關鍵詞實測，見 §2-1
4. **結構化標題**：每節用 H2 標題。判準是**「不看內文，能不能知道這節在講什麼」**——
   場景式問句可以用（「立法院有開放資料啦，為什麼這樣還不夠？」讀者立刻知道這節在講什麼），
   刻意扣住不說的懸念式不行（「然後，意想不到的事發生了」）。
   問句不是問題，**扣住不說才是問題**
5. **段落首句點題**：每段第一句說出該段重點，方便掃讀與摘錄
6. **連結帶完整名稱**：寫「[資源正式名稱](網址)」，不寫「點此」、「這裡」
7. **資源用小標題＋固定欄位呈現，不用表格**（2026-08-08 從表格改版）：每項資源一個
   `###` 小標題（資源正式名稱，含連結），底下固定「提供者」「用途」兩行。原因是表格轉純文字
   時容易被壓平黏成一團，而且 Medium 不支援表格語法。資源超過十幾個或欄位極短時例外，
   見 `templates/resource-list.md` 的適用邊界說明

## 使用方式

- 「我要寫一篇方法論文章」→ 選類型 A，從素材盤點開始
- 「幫我整理某領域的資源清單」→ 選類型 B，從素材盤點開始
- 「素材都有了，幫我列大綱」→ 從階段 2 開始
- 「草稿寫好了，幫我潤稿」→ 先過事實查核關卡，再進入風格套用
- 「這篇不屬於兩種類型」→ 走完整必問清單
