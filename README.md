# 台灣公民科技資料庫：人機協同寫作 pipeline

把編輯寫作的流程拆開，寫清楚**哪幾段交給 AI、哪幾段一定要人自己判斷**。

素材整理、大綱、初稿交給 AI；事實查核的最終把關、風格品味、要不要發表，由人決定。

**這不是「丟素材進去、按一個鈕生出文章」。** 寫作過程中 AI 會停下來問你問題，
要你確認方向。如果你要的是全自動生成，這套不適合你；但只要你願意在幾個關鍵點上
自己拍板，它能替你省下大量盤點、寫初稿的力氣。

文章結構也由模板定好，那個結構是為了讓 AI 切片段讀的時候每一塊站得住，
同時讓讀者一眼看出這篇能解決他什麼問題。

---

## 兩種文體，開始前先選一種

AI 會在一開始問你要寫哪一種。兩種的模板、結構與驗收條件都不同：

| 文體 | 寫給誰、寫什麼 |
|---|---|
| **方法論長文** | 讓提案者知道「具體該怎麼做」，提供可直接執行的方法 |
| **領域資源指南** | 讓正在規劃專案的提案者看懂某領域既有專案「怎麼做的」，能借鑑其機制設計，同時兼顧「這個領域有哪些資源可用」的索引功能 |

兩種的完整定義（目的、讀者、篇幅、結構）見
[`civic-tech-writing-pipeline/SKILL.md`](civic-tech-writing-pipeline/SKILL.md) 的「文章類型」一節。

## 你會做出什麼

走完一輪，你手上會有這些東西。**只有第一份會公開發表**，其餘留在你自己手上：

| 產出 | 在哪一站產出 | 對你的用處 |
|---|---|---|
| **文章本體** | ③ 初稿 | 可以直接發表的那一份 |
| **查核總表** | ④ 事實查核 | 有人質疑你哪一句時，翻得出出處，還有當初標的依據等級 |
| **引用網址清單** | ④ 事實查核 | 一年後連結死掉，知道要修哪幾條 |
| **執行環境自述** | 開始前（① 之前） | AI 開工前先自報家門，寫下它用什麼工具讀資料、從哪裡連網、有沒有子代理可以派、手上最強的推理模型是哪一個。半年後回頭改，你就知道哪些查核是人工補的 |
| **規則提案清單** | ⑥ 交付前驗收 | 這次撞到的坑寫下來，下次不用再撞一次 |
| **主張表**（只有寫方法論長文時會有） | ② 大綱 | 每一節到底想講什麼，一張表看完 |

**重點是**：你拿到的不只是一篇文章，是**一篇文章 ＋ 一份可以攤開給人看的稽核軌跡**。
有人問「這句話哪來的」「這個數字可靠嗎」，你翻得出來。這是直接叫 AI 寫一篇
給不了的東西。

（這是**交付時**要齊備的清單。過程中還會產生讀後憑證、關鍵詞檢索實測等中間產物，
那些是用來證明每一站真的做過，不算最後的交付物。）

## 怎麼裝：兩條路徑，挑一條

- **路徑一**：全程在瀏覽器裡，電腦上什麼都不用裝
- **路徑二**：你電腦上要先有一個 AI 工具（Claude Code、Antigravity 這類）

### 路徑一・約 3 分鐘・不需要懂程式

**開始前先確認兩件事：**

- **方案**：上傳自訂 skill 需要 claude.ai **Pro 以上**
  （依 [Claude 開發者文件](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)，
  2026-09-02 查證）
- **設定**：到 <https://claude.ai/settings/capabilities>，
  把「**Code execution and file creation**」打開。要開這個，是因為整包規則是用檔案的
  形式運作的。沒開的話 zip 解不開、讀不到裡面的檔

1. **下載壓縮檔**（zip，就是把一整包檔案壓成一個檔）：
   [civic-tech-writing-pipeline.zip](https://github.com/Legendream/AI-Writing-Skill/releases/latest/download/civic-tech-writing-pipeline.zip)
   （內容更新時這個檔案會自動換新，網址不變）
2. 開 <https://claude.ai/customize/skills>，把剛才下載的 zip 上傳上去。
   claude.ai 把這種「整包安裝的工作方式」叫做「**Skill**」。介面上看到這個字，
   指的就是這份東西。找不到這個頁面的話，直接在設定裡搜尋 `Skills`
3. 開新對話，跟 Claude 說「**我想寫一篇公民科技相關的文章**」

### 路徑二・讓 AI 自己去抓（電腦上有 Claude Code、Antigravity 這類工具的人）

開一個資料夾，跟 AI 說一句話：

> 請你把這個 repo 抓到這裡：https://github.com/Legendream/AI-Writing-Skill

（**repo** 就是 GitHub 上存放一整套檔案的地方，這裡指的就是上面那個網址。）

**2026-08-18 我們就是這樣把它交給 Antigravity 的**，後續跑完了一整篇文章。
你只要打這一句，抓檔案的事交給 AI 做。

同一次實測也讓我們確認了一件事：**流程跑得完，但交付前那道獨立驗收不能省**。

**你的素材放這個資料夾底下就好**：開一個叫 `素材` 的子資料夾，
連結、訪談筆記、PDF 都丟進去。這類工具讀得到你電腦上的檔案，
所以素材不用貼進對話，跟它說「素材在素材資料夾」就行。
（走路徑一的人不用做這件事，素材直接丟進對話裡。）

抓完之後，**每次開始寫的時候跟 AI 說一句**：

> 照你剛抓下來那包裡的 `civic-tech-writing-pipeline/SKILL.md` 進行

**「你剛抓下來那包裡」這幾個字要講**，它幫 AI 定位。抓下來會多一層以 repo 命名的
資料夾，講清楚了它才找得到。那包的最外層還有一份同名的 `SKILL.md`，那只是路標，
真正的流程在 `civic-tech-writing-pipeline/` 資料夾裡。

**每次都要講，覺得麻煩的話**，可以請 AI 把 `civic-tech-writing-pipeline` 資料夾
放進你的 skills 資料夾（Claude Code 是 `~/.claude/skills/`，Antigravity 是
`~/.gemini/config/skills/`）。放進去之後，你說想寫文章它就會自己叫出來。
**這個做法我們還沒實測**；上面那條抓到一般資料夾的做法才是驗證過的。

這包裡還附了一份檢查員設定檔（[`agents/article-reviewer.md`](agents/article-reviewer.md)），
用 Claude Code 的話可以派它幫你做交付前的獨立檢查。
**怎麼裝寫在 [`agents/README.md`](agents/README.md)**，一行 `cp` 指令的事。

**這是加分項，不是必需品。** 真正有效的是 `checklists/` 那份驗收條件清單，不是這個
設定檔。清單才是核心，不會因為沒有 Claude Code 就拿到殘缺版。
用聊天介面的人裝不了這個代理，改成開新對話貼清單就好；
**那個做法我們還沒實測過**（列在 [`docs/待辦總覽.md`](docs/待辦總覽.md) 的待測項目裡）。

### 用其他 AI 工具

**不是只有 claude.ai 能整包安裝。** Claude Code、Antigravity 這類讀得到檔案的工具，
用上面的路徑二就能裝起來，不需要把規則內容貼進對話。
純聊天介面沒有現成的 skill 可以裝，可以自己建一個帶知識檔的助理代替，
設計上同樣是建一次、之後開對話就有。
**底下這兩種做法我們都沒有實測過**，列出來是給你自己試的起點，不是我們驗證過的路徑：

- **ChatGPT**：建立 Custom GPT，把 `civic-tech-writing-pipeline/SKILL.md`
  （不是根目錄那份路標）與 `templates/` 上傳為知識檔，指示欄寫明
  「依 SKILL.md 的流程與查核關卡協作寫文章」
- **Gemini**：作法相同，建立 Gem 並上傳同樣那幾份檔案
- **不用 AI**：`checklists/` 可以當人工檢查表，`templates/` 可以當寫作大綱，
  流程本身是工具中立的

> **Custom GPT 與 Gem 這兩種，都不要用「把 `SKILL.md` 整份貼進對話框」代替。**
> 它有 33,042 字元（2026-09-03 量），而聊天對話不會記住，下一次開新對話得再貼一次。
>
> 至於上傳成知識檔，讀法是「需要時撈相關片段」、不是從頭讀完，
> 所以**建了 Custom GPT 或 Gem，也不代表流程會被照順序走**。
> **這一段是推論，我們沒有實測過**，跟網站常見問題那一題同一個把握度。
> 交付前那份檢查清單還是要你自己拿著對。

#### 交接給另一個 AI 時，直接複製這段

口述路徑很容易漏掉中間那層資料夾（實際發生過：說成 `AI-Writing-Skill/SKILL.md`，
接手的 AI 在根目錄找不到而卡住）。要交接時複製底下這段貼過去，不要憑記憶打路徑：

```
請依 civic-tech-writing-pipeline/SKILL.md 的流程與階段門檻協作寫文章。

入口與讀取順序：
1. civic-tech-writing-pipeline/SKILL.md（流程本體，先讀「開始前必問」與「文章類型」）
2. civic-tech-writing-pipeline/templates/（選定類型後複製對應模板）
3. civic-tech-writing-pipeline/checklists/（交付前驗收條件，動筆前先看一遍）
4. civic-tech-writing-pipeline/發布指引.md（發布前才需要）

注意：流程本體的 SKILL.md 在 civic-tech-writing-pipeline/ 底下，不是 repo 根目錄那一份；
根目錄的同名 SKILL.md 只是指向 civic-tech-writing-pipeline/SKILL.md 的路標，不含流程內容。
強制產物（讀後憑證、查核總表、檢索詞實測、規則提案清單）不可省略。
```

（根目錄另有一份 [`SKILL.md`](SKILL.md) 路標，指向真正的入口，供直接找根目錄的 AI 使用。）

#### 跨工具使用要注意兩件事

1. 用路徑二把 repo 抓到一般資料夾的話，AI 不會自動認出這套流程，
   **每次開始要明確指示「照這份流程進行」**。
   （Claude Code 與 Antigravity 都有各自的 skills 資料夾，放進去應該就會自動觸發，
   但**這個做法我們還沒實測**，見路徑二的進階做法。）
2. 流程中兩個環節依賴 AI 的工具能力：「讀後憑證」需要能實際連網讀取來源；
   「範圍型陳述的資料層抽驗」需要能下載檔案並執行程式。
   **若你的工具做不到，流程不會失效**：依據等級規則會自動把這類陳述留在需人工處理的等級
   （★★★☆☆ 以下），由人補做該項查核，只是人工介入的項目變多

本 pipeline 以在 Claude 環境順暢運作為標準。我們主要在 Claude 環境開發與測試，
各工具實測到哪裡見上面的工具表。

## 裝完之後，怎麼確認裝對了

照路徑一做完、開新對話後，Claude **不會立刻動筆**，而是先問你主題與素材範圍、
手上已有哪些素材，以及要寫哪一種文體。

**但「有問問題」不能當成裝成功的判準。** Claude 本來就會問問題。就算完全沒裝成功，
它也會問得很好、很像回事。我們自己實測時就被騙過：問題問得漂亮，
但用的根本不是這套流程。

**可靠的判準只有一個**：看它回覆的**最後一行是不是以「下一站：」開頭**。例如：

```
下一站：素材盤點
```

站名會隨進度變（素材盤點、大綱、初稿⋯⋯），但「下一站：」這個開頭是規則裡寫死的，
每一站結尾都會出現。**有這一行就是裝成功了**，沒有就是沒觸發到。
回頭確認路徑一的第 2 步，zip 是不是真的上傳好了。

**路徑二也用同一個判準**：這行來自規則本身，跟你用哪一種裝法無關。

> 📌 如果你的帳號裡還裝了其他寫作類的 skill，它們可能會搶走觸發。
> 介面上那行灰色的「讀取⋯⋯」標籤**不可靠**：它的文字是臨時生成的，
> 我們實測時看過三種不同寫法，其中一種還指向錯的 skill。一樣以最後那行為準。

## 八個階段，每站誰做什麼

| 站 | AI 做什麼 | 你做什麼 |
|---|---|---|
| **① 素材盤點** | 逐篇讀素材，交出讀過的證明，不是看標題腦補 | 素材不夠時，決定要縮小主題還是再找素材 |
| **② 大綱** | 排出章節結構，並列出關鍵詞的檢索結果 | 確認方向對不對、關鍵詞選得好不好，才會往下走 |
| **③ 初稿** | 把大綱寫成文章，每個事實旁邊標出處 | 這站先不用你出手，等 AI 寫完 |
| **④ 事實查核** | 逐條核對出處，標示每項查證的依據等級 | 依據等級偏低的內容，由你做最後判斷 |
| **⑤ 風格套用** | 依你給的風格檔或範文，調整全文語氣 | 開始前先給範文，或說清楚你想要的語氣 |
| **⑥ 交付前驗收** | 換一個沒看過草稿過程的「乾淨」AI 重新挑錯 | 決定要不要接受驗收結果 |
| **⑦ 精修** | 這一站交給你，AI 不主動動手 | **形式、取捨、語氣你說了算**：區塊留不留、段落併不併、標題怎麼寫 |
| **⑧ 發布** | 實測發布網址過不過三個硬門檻（人和 AI 找不找得到） | 決定發在哪裡、哪個網址算正本 |

寫**方法論長文**時，第 ② 站會多一步：AI 先列一張表，每一節填上「一句話主張、
什麼情況適用、案例、不做的代價」四欄（另有一欄「訣竅」可留空），等你確認**四個必填欄
都填得出來**，才進入下一站寫初稿。填不出來本身就是診斷結果：主張欄空白代表這一節
其實沒有重點，案例欄空白代表這個原則沒有實例撐得住。這是為了避免整篇寫完才發現
「看不出重點」，那時候要改，成本比改一格表格高很多。

> 這一節的分工以 [`docs/人機分工與外部回饋.md`](docs/人機分工與外部回饋.md) 為準。
> 那份文件改了，這裡要跟著改。

### 哪幾站可以省

| 能不能省 | 哪幾站 | 說明 |
|---|---|---|
| **不能略** | ① 素材盤點、④ 事實查核、⑥ 交付前驗收 | 這三站是這套東西唯一的賣點。略掉它們，就跟直接叫 AI 寫一篇沒有差別 |
| **可以收合** | ② 大綱、③ 初稿、⑤ 風格套用 | 趕時間可以併成一輪跑完。但**收合的只是「停下來等你確認」的節奏，產物不能省** |
| **看你要不要** | ⑧ 發布 | 只有要對外發表才需要走。**如果你寫的是內部文件、不打算公開，走到第 ⑦ 站就結束** |

⚠️ **最常被跳過、後果也最嚴重的是 ⑥ 交付前驗收。** AI 對自己工作的自評不可信。
第一篇正式交付的文章，就是靠一雙沒看過產出過程的眼睛才抓出 6 個規則層級的漏洞
（見 [`docs/驗收發現與規則提案_2026-08.md`](docs/驗收發現與規則提案_2026-08.md)）。

⑦ 精修沒有列在上面：**改多改少由你決定，但「人看過並且負責」這件事不能略。**
AI 整理出來的都算草稿，最後為文章負責的是你。

### 誰說了算：分界線

| 誰說了算 | 範圍 |
|---|---|
| **你** | 形式、取捨、語氣：區塊留不留、段落併不併、標題怎麼寫、要不要破例 |
| **不管誰改都不能錯** | 事實正確性、來源、授權、可攜性 |

### 第 ⑧ 站做完，值得多做一件事

發布之後，把**刊登網址貼回給 AI**，讓它比對「它交的草稿」與「你最後刊登的版本」。
好處依重要性排序：

1. **你的風格檔可能會更貼近你（未實測，值得你自己試一篇）。** 兩個版本的差異，
   就是你的風格檔還沒寫到的部分。把它歸納進 `styles/` 裡自己那一份，
   下一篇草稿*應該*會更接近你要的語氣。但這是推論，這套流程還沒實測驗證過
2. **順便確認發布網址 AI 讀不讀得到。** 真實案例：一篇文章用了 HackMD 的裸筆記網址，
   帶著「不要索引」的標記，發布好幾個小時都沒人發現它其實搜不到。
   這一步在 [`發布指引.md`](civic-tech-writing-pipeline/發布指引.md) 第八節本來就是強制的
3. **如果發現是這套流程沒防住的問題，順手記下來**（選配）。
   材料在做第 1 件事時已經產生了

## 改動這套 skill 的守則

`SKILL.md`、`templates/`、`checklists/`、`examples/` 是**同一組規則的四種投影**。
改了其中一份而沒改其他份，規則就會自相矛盾。

**動了 `templates/` 或 `SKILL.md` 的 PR，說明裡必須回答這兩題**（答「不用改」也要寫出來）：

1. `checklists/` 要不要跟著改？
2. `examples/` 要不要重生？

為什麼特別點名 `checklists/`：**規則寫進模板不等於生效，生效與否其實由驗收清單決定。**
模板是給寫作者看的建議，清單才是交付前的關卡。驗收員只照清單驗，清單沒寫的規則等於不存在。

還有兩條：

- **新增「放在文章開頭」的規則前，先確認它比「結構化資訊區塊」更該佔那個位置。**
  發布平台的摘要是從內文開頭截約 100 字（2026-08-08 更正，先前記載 150 字），
  那是稀缺版位，插什麼進去都會稀釋摘要句
- **裁決推翻了某條驗收條件時，先改條文再送獨立驗收。** 條文沒同步就送驗，
  驗收員會照舊條文把「刻意移除的東西」判成缺陷，而且那條假陽性通常排在報告最前面

三條的實例都在
[`docs/規則資產同步的診斷與提案_2026-08-07.md`](docs/規則資產同步的診斷與提案_2026-08-07.md)。

## 這套流程怎麼演化

規則不是設計出來的，是撞出來的：

```
實際寫一篇 → 出錯或被挑錯 → 問「為什麼這類錯漏得過去」
           → 寫成規則提案（docs/）→ 改 SKILL.md → 下一篇驗證
```

`SKILL.md` 裡「譯名絕不自創」「四類強制降級」「交付前送獨立驗收」等規則，
每一條都能在 `docs/` 找到它對應的那次犯錯。

**歡迎沿用這個方式**：用這套 skill 寫完文章後，若發現它沒防住某類錯誤，
把「為什麼漏得過去」寫下來。那比修好那一篇文章有價值得多。

## 維護政策

- `civic-tech-writing-pipeline/` 是交付主體，變更會反映在版本標籤上
- `docs/` 持續增補，每次獨立驗收後把「skill 沒防住的類型」寫成一份
- 平台實測結果（`發布指引.md`）會過期，文件內附有自行重測的方法，**請重測不要照抄**
