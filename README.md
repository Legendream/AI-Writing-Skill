# 公民科技知識庫：人機協同寫作 pipeline

一套可複製的寫作流程，讓社群貢獻者能與 AI 協作，產出**格式一致、事實可查證、
人類與 AI 都容易取用**的公民科技文章。

目標是降低「把知識整理成系統化文章」的門檻——不是讓 AI 代寫，
而是把「人該做什麼、AI 該做什麼、怎麼知道做對了」定義清楚。

---

## 五分鐘上手

1. 讀 [`civic-tech-writing-pipeline/SKILL.md`](civic-tech-writing-pipeline/SKILL.md) 的「文章類型」一節，選類型 A 或 B
2. 複製 [`templates/`](civic-tech-writing-pipeline/templates/) 裡對應的模板
3. 照 SKILL.md 的階段門檻走：素材盤點 → 大綱 → 初稿 → 事實查核 → 風格套用 → 交付
4. 交付前用 [`checklists/`](civic-tech-writing-pipeline/checklists/) 送獨立驗收
5. 發布前讀 [`發布指引.md`](civic-tech-writing-pipeline/發布指引.md)

---

## 流程地圖：哪個階段該看哪份文件

| 階段 | 你在做什麼 | 該看 |
|---|---|---|
| **開始前** | 決定寫什麼、給誰看 | `SKILL.md` →「開始前必問」「文章類型」 |
| **① 素材盤點** | 讀素材，證明真的讀過 | `SKILL.md` §1。**素材不夠時看 §1-4，不要硬寫** |
| **② 大綱** | 排結構 | `templates/` 對應文體的模板 |
| **③ 初稿** | 寫，並標註每個事實的來源 | 模板 ＋ `examples/` 看寫出來長什麼樣 |
| **④ 事實查核** | 產出查核總表、標依據等級 | `SKILL.md` §4。等級判準看 §4-1-1 |
| **⑤ 風格套用** | 調語氣 | `styles/` 的風格檔 |
| **⑥ 交付前驗收** | **換一雙沒看過過程的眼睛** | `checklists/` 對應文體的驗收條件 |
| **⑦ 發布** | 決定放哪個網址 | `發布指引.md` |
| **事後** | 把這次踩的坑變成規則 | `docs/` 看既有的規則提案怎麼寫 |

⚠️ 最常被跳過、後果最嚴重的兩關是 **⑥ 與 ⑦**：
自評不可信（見 `docs/驗收發現與規則提案_2026-08.md`），
而文章放錯網址等於沒發布（見 `發布指引.md`）。

## 資料夾地圖

```
SKILL.md                         ← 【路標】不是流程本體，指向下面那份

civic-tech-writing-pipeline/     ← 【交付主體】整個資料夾就是 skill，要用就複製它
├── SKILL.md                     流程本體：文章類型、階段門檻、查核關卡、格式規範
├── 發布指引.md                   文章放哪裡才被人與 AI 找得到（含平台實測比較）
├── templates/                   兩種文體的模板＋該用哪一份
├── checklists/                  交付前的獨立驗收條件（三種用法：代理／新對話／人工）
├── examples/                    實際範例文章＋導讀（導讀說明它示範了哪幾條規則）
└── styles/                      個人風格檔的說明與模板（風格可替換，流程共用）

docs/                            ← 【規則的依據】不是使用說明，是「為什麼」
├── 協作寫文章經驗回顧.md          這套流程的起源：第一次協作的逐輪紀錄與失敗案例
├── AI可讀性規範的依據.md          skill 規則自己的查核總表，含把握度與實測計畫
└── 驗收發現與規則提案_2026-08.md  第一篇交付文章驗收後暴露的 6 個規則漏洞

agents/                          ← 【選配加值】Claude Code 用的驗收代理定義
```

想直接用的人只需要 `civic-tech-writing-pipeline/`。
`docs/` 是給想知道「為什麼這樣規定」或要向別人交代的人看的。

⚠️ **PR 只交寫作方法本身，不要交文章成品。** 這個 repo 放的是 skill、模板、驗收清單
這些「怎麼寫」的資產；用這套流程產出的文章草稿與內部驗收紀錄（讀後憑證、查核總表、
檢索詞實測、規則提案清單）屬於你自己的專案，不屬於這裡，送 PR 前請確認沒有夾帶進來。

## 改動這套 skill 的守則

`SKILL.md`、`templates/`、`checklists/`、`examples/` 是**同一組規則的四種投影**。
改了其中一份而沒改其他份，規則就會自相矛盾。

**動了 `templates/` 或 `SKILL.md` 的 PR，說明裡必須回答這兩題**（答「不用改」也要寫出來）：

1. `checklists/` 要不要跟著改？
2. `examples/` 要不要重生？

為什麼特別點名 `checklists/`：**規則寫進模板不等於生效，生效與否其實由驗收清單決定。**
模板是給寫作者看的建議，清單才是交付前的關卡——驗收員只照清單驗，清單沒寫的規則等於不存在。

還有兩條：

- **新增「放在文章開頭」的規則前，先確認它比「本文重點」更該佔那個位置。**
  發布平台的摘要是從內文開頭截約 100 字（2026-08-08 更正，先前記載 150 字），
  那是稀缺版位，插什麼進去都會稀釋摘要句
- **裁決推翻了某條驗收條件時，先改條文再送獨立驗收。** 條文沒同步就送驗，
  驗收員會照舊條文把「刻意移除的東西」判成缺陷，而且那條假陽性通常排在報告最前面

三條的實例都在
[`docs/規則資產同步的診斷與提案_2026-08-07.md`](docs/規則資產同步的診斷與提案_2026-08-07.md)。

## 怎麼在各種工具上使用

**Claude Code**：把 `civic-tech-writing-pipeline/` 複製到 `~/.claude/skills/`，
之後提到「寫方法論文章」「整理資源清單」等需求時會自動觸發。
另可安裝 `agents/article-reviewer.md` 把交付前驗收自動化。

**claude.ai 網頁版**：把 `SKILL.md` 的內容（或本 repo 的 raw 連結）貼進對話，再開始寫作。

**ChatGPT**：單次使用把 `SKILL.md` 與所選模板貼進對話；重複使用可建立 Custom GPT，
把 `SKILL.md` 與 `templates/` 上傳為知識檔，指示欄寫明「依 SKILL.md 的流程與查核關卡協作寫文章」。

**Gemini**：作法相同，可貼進對話，或建立 Gem 並上傳檔案。

**不用 AI**：`checklists/` 可以當人工檢查表，`templates/` 可以當寫作大綱，流程本身是工具中立的。

### 交接給另一個 AI 時，直接複製這段

口述路徑很容易漏掉中間那層資料夾（實際發生過：說成 `AI-Writing-Skill/SKILL.md`，
接手的 AI 在根目錄找不到而卡住）。要交接時複製底下這段貼過去，不要憑記憶打路徑：

```
請依 civic-tech-writing-pipeline/SKILL.md 的流程與階段門檻協作寫文章。

入口與讀取順序：
1. civic-tech-writing-pipeline/SKILL.md（流程本體，先讀「開始前必問」與「文章類型」）
2. civic-tech-writing-pipeline/templates/（選定類型後複製對應模板）
3. civic-tech-writing-pipeline/checklists/（交付前驗收條件，動筆前先看一遍）
4. civic-tech-writing-pipeline/發布指引.md（發布前才需要）

注意：SKILL.md 不在 repo 根目錄，根目錄那份只是路標。
強制產物（讀後憑證、查核總表、檢索詞實測、規則提案清單）不可省略。
```

（根目錄另有一份 [`SKILL.md`](SKILL.md) 路標，指向真正的入口，供直接找根目錄的 AI 使用。）

### 跨工具使用要注意兩件事

1. 其他工具沒有 Claude 的技能自動觸發機制，每次開始要明確指示「照這份流程進行」
2. 流程中兩個環節依賴 AI 的工具能力：「讀後憑證」需要能實際連網讀取來源；
   「範圍型陳述的資料層抽驗」需要能下載檔案並執行程式。
   **若你的工具做不到，流程不會失效**——依據等級規則會自動把這類陳述留在需人工處理的等級
   （★★★☆☆ 以下），由人補做該項查核，只是人工介入的項目變多

本 pipeline 以在 Claude 環境順暢運作為標準，不保證在其他 AI 工具上的使用體驗。

## 人與 AI 的分工

- **人負責**：問題設定、選題判斷、事實查核的最終把關、風格品味、讀者判斷
- **AI 負責**：素材整理、大綱結構、初稿撰寫、格式查核、**主動標註不確定的資訊**

此技能不替使用者做最終事實把關。AI 必須主動標註每個事實的依據等級與待人類動作，
但每個事實的最終確認責任在人。

## 這套流程怎麼演化

規則不是設計出來的，是撞出來的：

```
實際寫一篇 → 出錯或被挑錯 → 問「為什麼這類錯漏得過去」
           → 寫成規則提案（docs/）→ 改 SKILL.md → 下一篇驗證
```

`SKILL.md` 裡「譯名絕不自創」「四類強制降級」「交付前送獨立驗收」等規則，
每一條都能在 `docs/` 找到它對應的那次犯錯。

**歡迎沿用這個方式**：用這套 skill 寫完文章後，若發現它沒防住某類錯誤，
把「為什麼漏得過去」寫下來——那比修好那一篇文章有價值得多。

---

## 維護政策

- `civic-tech-writing-pipeline/` 是交付主體，變更會反映在版本標籤上
- `docs/` 持續增補，每次獨立驗收後把「skill 沒防住的類型」寫成一份
- 平台實測結果（`發布指引.md`）會過期，文件內附有自行重測的方法，**請重測不要照抄**
