# 人機分工與外部回饋怎麼收

**這份文件記的是兩件從來沒落檔的事**：這套 pipeline 預設的人機分工是什麼，
以及開源之後別人回報使用經驗時，怎麼判斷哪些該進規則。

兩件事寫在一起，是因為第二件的判準完全建立在第一件上：**分工決定了哪些偏離是
「AI 做錯」、哪些是「人的判斷」**，而只有前者才是規則該處理的。

---

## 一、五段分工（Claire 拍板，2026-09-01）

```
AI 搜資料素材 → 跟人討論架構 → AI 寫草稿 → AI 套風格 → 人類精修
```

對應到 `SKILL.md` 的階段：

| 段 | 誰主導 | 對應章節 |
|---|---|---|
| 搜資料素材 | AI | §1 素材盤點 |
| 討論架構 | 人與 AI 一起 | §2 大綱、§2-0-2 主張表、§2-1 關鍵詞實測 |
| 寫草稿 | AI | §3 初稿、§4 事實查核 |
| 套風格 | AI | §5 風格套用 |
| **精修** | **人** | **目前沒有對應章節** |

### 為什麼要寫下來

2026-08-31 到 09-01 三批規則改動裡，有六項是同一個成因：
**規則預設「AI 從頭做到尾、人只在中間拍板」，所以把人在精修階段的判斷當成違規。**

| 作者在精修時做的事 | 規則原本怎麼判 |
|---|---|
| 拿掉延伸資源、資料來源清單 | 必備區塊，缺了不通過 |
| 把代價併進其他段落或刪掉 | 代價段必須存在 |
| 保留一個破折號 | 全文無破折號，硬條件 |
| 章標題改寫、索引跟著改 | 大綱定案後不得偏離 |
| 方法那節多包一層標題 | 層級寫死 H3／H4 |
| 主張表停在拍板版、不跟著改 | 要與定案版一致 |

六項全部改成「草稿必備、成稿由人判斷」或「不驗」。**但那是一項一項撞出來的**，
沒有撞到的還在。這份文件的用途之一，是讓下一次改規則的人先問一句：
**這條驗的是 AI 做錯，還是人的判斷？**

### 分界線

| 誰說了算 | 範圍 |
|---|---|
| **人** | 形式、取捨、語氣：區塊留不留、段落併不併、標題怎麼寫、破例 |
| **不管誰改都不能錯** | 事實正確性、來源、授權、可攜性 |

破例走既有機制：`_驗收紀錄/<篇名>_人工核准例外.md`（`SKILL.md` §6-1，2026-08-24 立）。

### 已知的缺口

**精修階段沒有回饋管道。** `SKILL.md` §6-5 的「skill 規則提案清單」是強制交付物，
立規緣由寫著「規則提案沒有交付物就會靜靜蒸發」——但它的時機在**交付時**，
也就是精修之前。作者改稿時發現的問題，改完就沒了，下一篇 AI 再犯一次。

**作者自述「每次都還是修滿多的」，而那一站正好是唯一沒有回饋管道的一站。**
補這個缺口（精修完回填一次提案清單）是目前投報率最高的改動，尚未實作。

## 二、外部回饋怎麼收

repo 是公開的。開源之後別人回報使用經驗時，用下面的判準決定要不要動規則。

### 第一刀：這是公版的事，還是他的聲音

`styles/README.md` 已經定好分工：

> **正確性與格式由公版強制，聲音由每位作者自帶一份風格檔。**

收到回饋先問這一句。屬於「他的聲音」的，答案是自帶風格檔或 fork，不是改公版。
**這一刀擋掉的量最大。**

### 第二刀：三類回饋，門檻不一樣

| 類型 | 幾次就夠 | 為什麼 |
|---|---|---|
| **正確性壞掉**：查核關卡沒擋住、授權標示錯、換一個 AI 執行就走樣 | **1 次** | 一個人撞到就是 bug，不需要累積 |
| **流程摩擦**：規則逼人做沒必要的工、規則自相矛盾、規則判不動 | **2 次，且來自不同領域** | 一個人覺得麻煩可能是他的做法特殊；不同領域都卡同一處才是通則 |
| **文風偏好**：想要更活潑／更學術／不同的小標習慣 | **永遠不夠** | 收進公版會讓文章千篇一律，違反 `styles/README.md` 的設計 |

「不同領域」這個限定很重要。兩個都在寫議會監督的人抱怨同一件事，
可能只是那個領域的特性。

### 第三刀：資料量什麼時候夠

不是看數量，是看**能不能講出這條規則要防的具體事故**：

> 我能不能寫出一段「某某在什麼情況下做了什麼，結果出了什麼問題」？

寫得出來就夠，一次也行。寫不出來，十個人說也不夠——那代表收到的是意見不是證據。
這一刀直接沿用 `docs/` 既有的立規紀律（從實際摩擦點出發、附具體證據、先診斷再立規）。

### 因此 issue 範本要問什麼

範本的目的不是問「你覺得怎樣」，是**逼對方交出那段事故描述**：

1. 你用哪一種文體、寫什麼主題
2. **AI 交的草稿，你精修時改了什麼**（貼出改之前、改之後）
3. 為什麼改：AI 寫錯／規則害的／個人偏好

第 3 題最重要。前兩種收，第三種轉給風格檔或 fork。

### Fork 是正確答案的一部分，不是退路

如果需求落在「文風、領域慣例、特殊交付格式」，fork 對雙方都好：
公版不必為了容納個案而變成一堆例外的妥協。2026-08-31 到 09-01 那三批已經證明，
規則一旦開始為個案讓步，很快會互相打架。

`README` 應該直接寫明：**文風與領域慣例請自帶風格檔或 fork；
回報 issue 請限於正確性問題與流程摩擦。**

### 收進來之後

走既有的 `docs/規則提案總帳.md`。它本來就在做「哪些提案累積到第二次了」的
集中檢視，外部回饋當成新的一列即可，不需要另建機制。
