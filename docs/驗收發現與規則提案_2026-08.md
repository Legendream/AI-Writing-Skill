# 驗收發現與規則提案（2026 年 8 月）

> **這份文件記錄的是：第一篇正式交付文章送獨立驗收後，暴露出 skill 沒防住的問題類型。**
>
> 個別文章的錯誤修完就結束，不值得記錄。有長期價值的是「**這一類錯誤為什麼漏得過去**」——
> `SKILL.md` 的規則就是這樣一條一條長出來的（前一份證據見
> [`協作寫文章經驗回顧.md`](協作寫文章經驗回顧.md)）。

## 事件

- **文章**：《政府的錢花去哪了？預算、標案、補助的查詢工具一次找齊》（類型 B，第一篇正式交付）
- **驗收方式**：獨立驗收員，只給驗收條件與檔案位置，不給產出過程
- **結果**：22 條驗收條件通過 15 條、不通過 7 條；判定「修正後可交付」；
  另有 6 項條件外發現
- **關鍵事實**：這篇文章交付時，**skill 內建的強制查核關卡是全數自評通過的**

最後這點是整份文件的重點。關卡沒有失效，是**自評這個機制本身不可信**。

## 六個規則層級的漏洞

### 漏洞 1：自評與實際脫鉤

| | |
|---|---|
| **現象** | 強制關卡自評「專有名詞首次出現有括號說明 ✅」，實際上 API、XML、Cloudflare、READr、WTO、g0v 六個都沒說明；自評「具體事實均有來源 ✅」，實際查核總表漏了六類事實 |
| **為什麼漏得過去** | 同一條對話脈絡裡的 AI 會傾向確認自己剛做過的判斷。它記得自己「有在注意專有名詞」，於是打勾，而沒有回頭逐個數 |
| **提案** | 交付前強制送**獨立驗收**——換一雙沒看過產出過程的眼睛。並把驗收條件寫成可重複使用的清單，讓沒有子代理環境的人也能用（開新對話貼清單，或人工逐條打勾）|
| **狀態** | ✅ 已實作：`SKILL.md` §6-1、`checklists/` 兩份清單 |

### 漏洞 2：依據等級的上限沒有機制檢查

| | |
|---|---|
| **現象** | 兩處「結構性證據」都被標成 ★★★★☆，超過規則允許的 ★★★☆☆ 上限。其中一處（某平台的提供者歸屬）的結構性證據本身還被頁面上的品牌訊號推翻 |
| **為什麼漏得過去** | 上限只寫在條文裡靠自律，沒有任何檢查點會攔截 |
| **提案** | 列入驗收條件，由獨立驗收員逐項核對「依據類型」與「依據等級」是否相稱 |
| **狀態** | ✅ 已實作：兩份 `checklists/` 皆列為條件 |

### 漏洞 3：沒有處理時效性衰減

| | |
|---|---|
| **現象** | 文章中一個資源的連結，在交付後**三週**被該單位改成轉址，指向清單裡的另一個資源。撰稿當時完全正確 |
| **為什麼漏得過去** | skill 只管「寫的當下對不對」，沒有任何規則處理「多久之後會不對」|
| **提案** | 尚未實作。可能方向：資源清單標註查核日期；交付時附「建議複檢週期」；驗收條件加入「實際開啟每個連結，確認到達的還是文章描述的那個東西」 |
| **狀態** | ⚠️ 部分實作：驗收條件已加入連結實檢與轉址檢查；**「複檢週期」尚未納入 SKILL.md**，待下次修訂 |

### 漏洞 4：內部術語外洩到對外文章

| | |
|---|---|
| **現象** | 交付文章的查核聲明裡出現「待人類」「讀後憑證」「強制查核關卡」「（發布時狀態）」，這些對讀者毫無意義；星級量表也沒有圖例 |
| **為什麼漏得過去** | `SKILL.md` §6 要求交付時附查核聲明，但**沒規定要轉譯成對外語言** |
| **提案** | §6 增列「查核聲明要轉譯成對外語言；使用量表必須附圖例」|
| **狀態** | ✅ 已實作：`SKILL.md` §6 |

### 漏洞 5：素材盤點只管「有沒有讀」，不管「改寫程度」

| | |
|---|---|
| **現象** | 文章的領域簡介幾乎逐句沿用某廠商產品頁的行銷文案，而該來源**不在資料來源清單裡**；且原文只講一類資料，正文擴大成三類 |
| **為什麼漏得過去** | 素材盤點的規則是「要證明讀過」，讀過之後**改寫到什麼程度才算自己的話**沒有規範；引述來源要不要入清單也沒明說 |
| **提案** | 尚未實作。方向：素材盤點增列「引述聲明」——凡是句式結構沿用來源的段落，必須標出來源並入清單；且不得用單一廠商的說法當領域的中立描述 |
| **狀態** | ⚠️ 部分實作：驗收條件已列入檢查；**SKILL.md 尚未增列規則**，待下次修訂 |

### 漏洞 6：查核總表的顆粒度沒有定義

| | |
|---|---|
| **現象** | 修辭性的數量詞（「數百份 PDF」）、日期（「2015 年 4 月起」）、延伸閱讀的內容描述都沒進總表 |
| **為什麼漏得過去** | 「一個事實陳述」到底指多大一塊，規則沒說。寫的人自然會挑「看起來像事實」的句子列，跳過看起來像修辭的 |
| **提案** | 尚未實作。方向：明確定義「凡是讀者可能拿去引用、或錯了會誤導的陳述，都是一個事實陳述」，並舉例說明修辭性數量詞也算 |
| **狀態** | ❌ 未實作，待下次修訂 |

## 這次沒有改動的判斷題

有一項驗收發現屬於**編輯判斷，不是對錯**，記錄下來供日後決定：

**「此網站可能阻擋境外 IP」這句話該不該留在正文？**

- 驗收員認為它更像查核過程的備註外洩到正文，對多在台灣的目標讀者沒有作用，建議移到查核聲明
- 但這句正是 `examples/` 導讀裡當成典範的做法——「查核踩到的坑本身就是讀者會踩的坑」
- 兩種說法都成立。拍板結果應回饋到 `SKILL.md`，因為它決定了「查核過程的副產品要不要寫進正文」這條通則
- **狀態**：待作者拍板

## 給後續使用者的一句話

如果你只從這份文件帶走一件事：**不要相信 AI 對自己工作的自評**，包括這套 skill 內建的
強制查核關卡。那份自評的用途是「讓你知道該查什麼」，不是「證明已經查過了」。
真正的關卡是交付前那雙沒看過產出過程的眼睛。
